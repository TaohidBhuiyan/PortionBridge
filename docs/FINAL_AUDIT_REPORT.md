# PortionBridge — Final integration & production-readiness audit (Phase 6)

Everything below is labelled **VERIFIED** (executed in this audit, result stated), **FIXED**, or **NOT VERIFIED / RECOMMENDATION**. The application is **not declared "completely secure" or "production-ready"**: see sections 7–8.

## 1. Executive summary
The disaster-response feature (Phases 0–5) integrates cleanly with the donation platform. The full backend suite passes **260/260 on the working database and 260/260 on a separately created database built only from `main_schema.sql` + `triggers.sql` + `npm run migrate`** (proving a clean install works). Client: 254/254 tests, production build OK, lint unchanged from the original baseline. The audit found and fixed **one critical latent defect in the migration runner, one hard-coded admin credential in a seed script, one data-integrity gap introduced in Phase 5, a stale test and a `.gitignore` gap**. The one item first left open (C2: three scripts with unresolved git merge-conflict markers) was **resolved in the follow-up repair** (section 2, C2) and is now guarded by a test. After the repair the backend suite is **265/265 on both databases** (working DB and a freshly built isolated DB).

## 2. Issues found
**Critical**
- C1 FIXED — *Migration runner wrote to the wrong database.* 14 historical migrations start with `USE portionbridge;`. With any other `DB_NAME` (e.g. a test database) the runner silently switched to a database literally named `portionbridge`, ran later migrations there and read the wrong `schema_migrations`. Fix: the runner strips `USE …;` lines and re-selects the configured database after every migration (historical files untouched). VERIFIED: fresh isolated DB now gets 021, 028–032 applied and 46 tables, identical to the working DB; `stripUseStatements` covered by `tests/unit/migrateRunner.test.js` (3 tests, run separately after the full-suite runs: pass).
- C2 FIXED (follow-up repair) — *Unresolved merge-conflict markers in `seedDummyData.js` (102 blocks), `seedNearbyOpportunities.js` (142) and `backupDatabase.js` (4), present in the original upload.* The ZIP contains no `.git` directory, so **no Git history was available**; each conflict was resolved from the code itself, the schema and the neighbouring scripts. A blind "ours" or "theirs" is wrong for all three (it either loses features, duplicates rows, leaves empty loops or leaves a runtime `ReferenceError`), so each was merged by intent:
  - `backupDatabase.js` (SQL dump / `restore` / `list`; not referenced by any npm script, doc or code — `npm run backup` uses `simpleBackup.js`, a different JSON format, so this is *not* obsolete and was kept): one row-handling loop (the older variant had been left next to the newer one and would have written every row twice); the intended "invalid date → NULL" guard now works (`toISOString()` throws on an invalid Date, so the old check never fired and the row was skipped).
  - `seedNearbyOpportunities.js`: keeps the `pickup_address_details` coordinate objects (the script's purpose is location-based discovery) and serialises them to JSON on insert.
  - `seedDummyData.js`: keeps the larger sample set and the volunteer-activity seeding, plus the other branch's fixes (`allergens` is a JSON column; `donorId` was referenced but never defined in the larger variant → would have crashed at runtime although `node --check` passed).
  Running them against a scratch database (never the real one) then exposed **schema drift that predates the conflicts and had to be fixed for the scripts to work at all**: `donation_requests.pickup_time` is NOT NULL (now derived from `pickup_date` + slot with the same clock times the older `importDummyDonations.js` uses); `is_vegetarian`/`is_halal`/`refrigeration_required` are ENUMs, not booleans; `clothing_category` `'other'` → `'others'`; hard-coded numeric `donor_id` values (9–15) only matched the author's database and could attribute a donation to the wrong person elsewhere — donors are now resolved by the names already written beside them. Two **restore** defects in `backupDatabase.js` that made it impossible to restore were fixed: the restore connection selected no database, and views (`top_donors`, `top_volunteers`) were dumped as `undefined;` and, once fixed, with the *source* database name embedded (a restore into another database would have written to the source — the same class of defect as C1); views are now dumped definition-only, without DEFINER or database qualifier. **VERIFIED (scratch databases only):** seeds ran (see section 7), a backup of the seeded scratch DB restored into a second empty DB with **identical row counts and checksums for all 44 tables, both views, and the same foreign-key count**; the real `portionbridge` database was unchanged before/after. A new unit test (`tests/unit/sourceIntegrity.test.js`) fails the suite on any conflict marker in the source tree or any server `.js` file that does not parse (shown to fail when a marker is planted).
- C3 FIXED — `seedAdmin.js` hard-coded an admin e-mail and plaintext password in source. It now requires `SEED_ADMIN_EMAIL` / `SEED_ADMIN_PASSWORD` (policy-validated) and refuses to run without them (VERIFIED). **Rotate that account's password if it ever existed in a real deployment.** `seedDemoUsers.js`, `seedRandomUsers.js` (and the broken `seedDummyData.js`) still contain demo-user passwords: development-only, never run them on a real database. `seedDummyData.js` also embeds real-looking personal e-mail addresses and a phone number in its sample users — consider replacing them with placeholders before the repository is shared.

**Major**
- M1 FIXED — (Phase 5) an admin could still edit a *merged* duplicate incident. Now 409; covered by a new test.
- M2 FIXED — root `.gitignore` did not ignore `.env` files (only `portionbridge/.gitignore` did). Added `.env`, `.env.*` (keeping `*.example`).
- M3 FIXED (test) — `achievement.test.js` failed on the *original* upload: its premise ("completeDonation does not auto-check volunteer achievements") is outdated because `donation.service.js` now does. The test was updated to assert the current behaviour **and** the original intent (volunteer-only achievements for the volunteer, none for the donor); not removed or weakened.

**Minor / documentation**
- `VITE_DEV_MODE` and `ALERT_STALE_CLAIM_SECONDS` were undocumented → added to the `.env.example` files. `VITE_DEV_MODE=true` shows a dev-login button whose server endpoint (`/auth/dev-login`) **does not exist** (VERIFIED by code search) — harmless dead UI, keep it unset in production.
- `docker-compose*.yml` use the placeholder password `examplepassword` — replace before real use.

## 4. Disaster workflow — VERIFIED end to end (`phase6Integration.test.js`, `adminOps.test.js`, `relief*.test.js`, `disasterAlerts.test.js`)
report (cannot self-verify) → admin verify (incident public with *approximate* coordinates, never the address) → approve request → pledge → volunteer accept/pickup → delivery *reported* (not counted) → admin verify (partial allowed) → remaining need re-opens → complete → request auto-completes → incident resolved → no further pledges. The same figures are asserted on the public summary, donor "my pledges", volunteer tasks, admin dashboard and reports. Two items with different units (pieces vs packets) are never added together. Parallel verifies of one report produce exactly one success; parallel corrections never double count; repeated alert triggers/sweeps never duplicate a notification; a simulated notification outage does not roll back assignment or verification.
Transitions for every status model are documented in `docs/STATUS_TRANSITIONS.md` and checked by tests (DB enums ↔ code constants for 21 columns, transition graphs, merged/terminal behaviour).

## 5. Database and migrations
VERIFIED: forward order 021 → 028 → 029 → 030 → 031 → 032 on a fresh and on the working DB; 031 and 032 down+up round trips; all Phase 4/5 changes additive; FKs use `CASCADE` for alert/outbox rows tied to an incident and `SET NULL` for actor columns; indexes exist for inbox, outbox queue and alert lookups. NOT VERIFIED: behaviour on a very large production dataset (no load test); the *down* scripts were tested for 031/032 only. Order, backup and rollback procedure: `database/migrations/README.md`, `docs/SETUP_AND_DEPLOYMENT.md`. Migrations 029–032 are not folded into `main_schema.sql` by design (incremental installs).

## 6. API and security changes in this phase
- Migration runner hardened (C1); `seedAdmin` credentials removed (C3); merged incidents read-only (M1); `.gitignore` (M2).
- VERIFIED by tests: every `/admin/ops/*` route and every alert-publishing/escalation/cancel route rejects donors, volunteers and anonymous callers; filters/dates/enums are validated (SQL never receives user text except as bound parameters; dynamic identifiers use whitelists — heuristic review of all `${…}` interpolations in models/services, not a proof); mass-assignment attempts on assign/verify endpoints are ignored; notifications are only readable/markable by their owner; sockets reject bad tokens and deliver only to the recipient; exports contain no names/phones/emails/addresses and neutralise spreadsheet formulas.
- Route inventory: all `/api/v1` routes without an auth middleware in their own stack were reviewed; the ones left are the intentionally public ones (login/registration/password flows, health, master data, public stats and public volunteer profile, anonymous read-only relief map data that is already limited to verified incidents) or sit behind a router-level `protect` (admin ops, saved addresses) — confirmed with live unauthenticated requests (401/403).
- Existing protections retained and exercised by tests: bcrypt hashing, JWT access/refresh with reuse detection, CSRF token helpers, image magic-byte validation on uploads, rate limiters.

## 8. Known limitations, skipped checks, unresolved items
- Client lint debt (118 problems: 99 `no-unused-vars`, 12 `react-hooks/set-state-in-effect`, 3 `exhaustive-deps`, 2 `static-components`, 1 `no-useless-assignment`, 1 `only-export-components`, spread over 44 files) is **identical to the original upload and none of it is in files added during the disaster phases**; it was not suppressed or refactored (risk of regressions).
- Seed/backup scripts: `seedRandomUsers.js` (no conflict markers; outside C2) still exits 1 after creating its users because of a stale `vehicle_type` ENUM value — not touched. `seedDummyData.js` creates its donations again on every run (users are idempotent): run once, on a development database only. `backupDatabase.js restore` drops and recreates every table in `DB_NAME`: it warns, but double-check `DB_NAME` first. Dumps contain real data and are written to `portionbridge/backups/` (git-ignored) — protect them like the database.
- The conflicts were resolved without Git history (the ZIP has no `.git`); review the three files' diff in Git before merging.
- Not performed: browser/E2E, accessibility audit with assistive tech, load/performance testing at scale, `npm audit`, penetration testing, real SMTP/OAuth/proxy/TLS/WebSocket-through-proxy checks, Docker-compose run, map tile loading from a deployment origin. Passing automated tests does not establish that the application is secure.
- Product/policy decisions left unchanged (documented, not silently altered): a *resolved* incident keeps its approved requests (flagged "needs reassessment") and tasks already in progress may finish; a single `admin` role (no finer permissions); no upazila data model; alerts are in-app only (no SMS/e-mail/push); the alert sweeper is in-process; public OSM tile/Nominatim services need a production plan.
- Incident/request history before Phase 5 exists only in the audit log.
- The recommended Git procedure and manual pre-deploy checklist are in `docs/SETUP_AND_DEPLOYMENT.md`.
